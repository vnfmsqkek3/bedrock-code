IDP vs Bedrock Knowledge Base

내 문서를 올려 AI 챗봇이 근거를 갖고 답하게 하는 두 가지 방법 — AWS 관리형 Bedrock KB와 직접 만든 IDP 파이프라인을 쉽게 비교합니다.

Bedrock KB — 관리형 IDP — 직접 구축

IDP vs Bedrock Knowledge Base — 쉽게 이해하기

AWS/Bedrock을 몰라도 이해할 수 있게 쓴 비교 문서입니다. 비교 대상: IDP(megazone-idp, 직접 만든 문서분석 파이프라인) vs Bedrock KB(csc-genai-lab, AWS 관리형 지식베이스).

0. 30초 요약 (TL;DR)

둘 다 "내 문서를 올리면, 그 문서 내용을 근거로 챗봇이 답하게 해주는" 시스템입니다(이걸 RAG라고 부릅니다). 차이는 누가 얼마나 만들어주느냐입니다.

Bedrock KB IDP (직접 구축)
한 줄 AWS가 대부분 알아서 해주는 관리형 처음부터 끝까지 직접 만든 파이프라인
만드는 노력 적음 (설정 몇 개) 많음 (14개 스택, 수십 개 부품)
문서 이해 방식 텍스트 추출 → 잘라서 저장 페이지를 이미지로 보고 AI가 분석
부가 기능 검색 위주 지식그래프·자동분류·폴더트리·요약 등
비용/유연성 저렴·단순, 세밀한 제어는 포기 비싸고 복잡, 무엇이든 커스터마이즈

핵심: "AI가 알아서 답하는 챗봇"이라는 결과는 비슷합니다. 차이는 인프라와 제어 수준입니다.

1. 그 전에 — "그냥 AI(ChatGPT 등)에 문서 붙여넣는 것"과 뭐가 다른가?

가장 헷갈리는 부분부터 짚습니다.

그냥 AI에 파일 붙여넣기 = 대화 한 번에 문서를 통째로 넣고 물어보는 것. - 👍 간단하다. - 👎 대화가 끝나면 사라진다. 다음에 또 통째로 붙여야 한다. - 👎 문서가 수백~수천 개면 한 번에 못 넣는다(AI가 한 번에 읽을 수 있는 양엔 한계가 있음). - 👎 "우리 회사 전체 자료에서 찾아줘" 같은 건 불가능.

KB / IDP (RAG 방식) = 문서를 미리 잘게 쪼개 색인(index)해 저장해두고, 질문이 오면 관련 조각만 꺼내서 AI에게 준다. - 👍 한 번 올리면 영구히 재사용. 다음에 또 안 올려도 됨. - 👍 문서가 수만 개여도 관련된 부분만 골라 쓰니 문제없음. - 👍 "출처가 어느 문서 몇 페이지인지" 표시 가능.

비유: 그냥 붙여넣기 = 매번 책 한 권을 통째로 읽어달라고 부탁. RAG = 도서관에 색인(index)을 만들어두고, 질문에 맞는 페이지만 펼쳐 보는 것.

KB와 IDP는 둘 다 이 "도서관+색인" 방식입니다.

2. Bedrock KB란?

Amazon Bedrock Knowledge Base = AWS가 제공하는 관리형 RAG 서비스. "문서 올리면 검색 가능한 지식베이스로 만들어 주세요"를 버튼 몇 번으로 해줍니다.

내부적으로 이런 부품을 AWS가 알아서 굴립니다: - 저장소(데이터 소스): S3(파일 보관함)에 문서를 올림 - 파싱(Parsing): 문서에서 글자를 뽑아냄 (아래 3가지 중 선택) - DEFAULT — 기본 텍스트 추출 - FOUNDATION_MODEL — Claude(Sonnet)로 페이지를 보고 표·이미지까지 해석 - DATA_AUTOMATION — AWS BDA로 OCR·표·레이아웃 추출 - 청킹(Chunking): 뽑아낸 텍스트를 조각으로 자름 (뒤에서 자세히) - 임베딩(Embedding): 각 조각을 숫자 벡터로 변환 (Titan Embed Text V2, 1024차원) - 벡터 저장소: OpenSearch Serverless에 벡터를 저장(검색용 색인) - 검색+답변: RetrieveAndGenerate API가 질문에 맞는 조각을 찾아 Claude가 답을 생성

즉 KB의 일은 "문서 → 파싱 → 청킹 → 임베딩 → 저장 → 검색"을 AWS가 자동으로. 개발자는 청킹 방식·파서·임베딩 모델만 고르면 끝.

3. IDP란?

IDP(Intelligent Document Processing) = 위와 같은 일을 AWS 서비스들을 직접 조립해서 만든 파이프라인(megazone-idp). KB가 "완제품"이면 IDP는 "직접 만든 공장"입니다.

가장 큰 차이: IDP는 문서를 "텍스트"가 아니라 "그림(이미지)"으로도 봅니다. - 각 페이지를 이미지로 렌더링한 뒤, 비전(vision) AI(Claude)가 페이지를 눈으로 보고 도표·차트·레이아웃까지 이해해서 분석문을 새로 씁니다. - 그 "AI가 이해한 분석 결과"를 색인합니다. (원문 텍스트만이 아니라 가공된 이해를 저장)

그리고 검색 말고도 여러 부품을 직접 얹었습니다: - 지식그래프(Neptune) — 문서에서 인물·조직·개념(엔티티)을 뽑아 연결 - 자동 분류 — 문서를 폴더 카테고리로 자동 정리 - 폴더 트리 UI, 실시간 진행상황, 문서 요약 등

4. 문서를 넣으면 각각 어떻게 동작하나 (핵심 비교)

Bedrock KB — "잘라서 담는다"

1. S3에 문서 업로드
2. 동기화(Ingestion) 시작
3. 파싱  : 문서에서 텍스트 추출 (필요시 Claude/BDA로 표·이미지 해석)
4. 청킹  : 텍스트를 조각으로 자름 (기본 semantic, 500토큰)
5. 임베딩: 각 조각 → 숫자벡터 (Titan V2, 1024차원)
6. 저장  : OpenSearch에 벡터 색인
→ 끝. 이제 검색 가능

파싱을 강하게(FOUNDATION_MODEL/BDA) 켜면 스캔본·표·이미지도 잘 읽습니다.

IDP — "이해하고 담는다"

1. 업로드 → S3 (EventBridge가 감지)
2. 타입 감지 : PDF/이미지/텍스트/HTML 등 판별해 처리 경로 결정
3. 전처리(동시에):
   - 페이지를 이미지로 렌더링
   - OCR(글자인식) / BDA(표·레이아웃) / 텍스트 추출
4. 세그먼트 조립: 페이지별로 이미지+텍스트를 묶음
5. 분석  : 비전 AI(Claude)가 페이지를 "보고" 질문-답변식으로 심층 분석 (여러 번 반복)
6. 색인  : 분석 결과를 임베딩(Titan V2) → LanceDB(벡터+키워드 검색)
7. 그래프: 엔티티 추출 → Neptune 지식그래프
8. 요약·자동분류 → 완료

→ KB보다 무겁지만, 페이지를 눈으로 보고 분석하므로 스캔본·도표·인포그래픽에서 원문 텍스트가 놓치는 걸 더 잘 잡고, 그래프·자동분류 같은 부가정보를 만듭니다.

5. 청킹(Chunking)이란? — 왜 자르나

청킹 = 긴 문서를 검색하기 좋은 "조각(청크)"으로 자르는 것.

왜 자르나? AI에게 관련 부분만 딱 집어 주려면, 문서를 통째가 아니라 작은 단위로 저장해야 하기 때문입니다. - 질문 = "환불 규정?" → 문서 전체가 아니라 관련 청크 몇 개만 꺼내 AI에 전달. - 조각이 너무 크면: 관련 없는 내용이 섞여 검색이 부정확하고 AI가 헷갈림. - 조각이 너무 작으면: 문맥이 끊겨 "무슨 얘기였는지" 앞뒤가 사라짐. - 그래서 "얼마나, 어떤 기준으로 자르냐"가 검색 품질을 좌우합니다. 이게 청킹 전략입니다.

토큰(token)? ≈ 단어 조각. "안녕하세요"가 대략 2~3토큰. 500토큰 ≈ 300~400단어(대략 한 문단~반 페이지) 정도.

대표적인 청킹 방식 4가지 (일반 개념)

문서 종류·서비스와 무관하게, RAG에서 자주 쓰이는 방식은 대략 이 넷입니다.

① 고정 크기 (Fixed-size) - 개념: 의미와 상관없이 정해진 길이(예: 500토큰)로 뚝뚝 자름. 보통 조각끼리 앞뒤를 조금 겹치게(overlap) 해서 경계에서 문맥이 끊기는 걸 완화. - 👍 단순·빠르고 예측 가능. 👎 문장이나 표 한가운데서 잘릴 수 있음. - 비유: 책을 내용 안 보고 10줄마다 기계적으로 찢는 것.

② 의미 기반 (Semantic) - 개념: 문장들의 의미가 비슷한 곳끼리 묶고, 화제가 바뀌는 지점에서 자름. "여기서 주제가 바뀌네" 하는 경계를 찾아 자연스러운 덩어리를 만듦. - 👍 문맥이 잘 안 끊겨 검색 품질이 좋음. 👎 계산이 더 무겁고 조각 크기가 들쭉날쭉. - 비유: 책을 읽어보고 "장/절이 바뀌는 데" 에서 나누는 것.

③ 계층 기반 (Hierarchical) - 개념: 큰 조각(부모)과 작은 조각(자식)을 같이 만듦. 검색은 작은 조각으로 정밀하게 하고, AI에게 넘길 때는 그 조각이 속한 큰 조각(넓은 문맥)을 함께 줌. - 👍 "정확히 찾기"와 "넓은 문맥 주기"를 둘 다 챙김. 👎 구조가 복잡하고 저장량이 늘어남. - 비유: "몇 페이지"로 정확히 찾되, 답할 땐 그 페이지가 든 "챕터 전체"를 같이 펼쳐 보는 것.

④ 안 자름 (None) - 개념: 파일 하나를 통째로 한 조각 취급. 문서가 짧거나 이미 잘게 나뉜 경우에 씀.

KB는 이 방식들을 "설정으로 골라" 씀

Bedrock KB는 위 4가지를 옵션으로 제공하고, 개발자가 처음에 하나를 고릅니다(기본은 의미 기반).

⚠️ KB는 청킹 방식을 처음 만들 때 정하면 나중에 못 바꿉니다(바꾸려면 데이터소스 재생성).

IDP는? — "청킹 전략을 고르는 개념이 아님"

IDP는 위처럼 semantic/hierarchical 중 하나를 고르는 구조가 아닙니다. 대신 문서 종류에 따라 자르는 기준 자체가 다릅니다.

방식 IDP에 있나? 설명
페이지 단위 (그림/PDF) ✅ 핵심 방식 한 페이지 = 한 조각(세그먼트). 페이지를 이미지로 보고 통째로 분석·저장
고정 크기 (글 문서) ✅ 있음 텍스트/HTML/MD는 일정 길이로 잘라 청크 생성(겹침 포함)
의미 기반 (semantic) ❌ 없음 화제 전환을 찾아 자르는 방식은 쓰지 않음
계층 기반 (hierarchical) ❌ 없음 부모/자식 청크 구조는 없음
  • 즉 IDP는 "어떻게 자를지 고르는" 게 아니라, 문서가 그림이면 페이지째, 글이면 길이째로 자동 결정합니다.
  • 대신 IDP는 "잘라서 저장"에 그치지 않고, 각 페이지를 AI가 보고 이해한 분석문을 만들어 저장하므로(3·4절), 청킹 전략의 정교함보다 페이지 단위 심층 이해로 승부하는 구조입니다.

정리: KB = 청킹 전략을 메뉴에서 고른다(의미/계층/고정/없음). IDP = 청킹을 고르지 않고, 문서 종류에 맞춰 페이지·길이로 자동 분할한다(의미/계층 방식은 없음).

6. 메타데이터(Metadata)란?

메타데이터 = 문서 내용이 아니라, 문서에 "딸린 정보"(꼬리표).

예: 문서 본문은 "Bedrock 사용량 한도는..."이지만, 메타데이터는 그 문서가 어떤 종류/주제/연도/폴더인지를 따로 붙인 것.

왜 필요한가 (일반 개념)

벡터 검색만으로는 "의미가 비슷한 조각"은 잘 찾지만, "2023년 문서만", "계약서 종류만" 같은 딱 떨어지는 조건은 걸러내기 어렵습니다. 메타데이터는 이 빈틈을 메웁니다. - 필터링: "이 조건에 맞는 문서 안에서만 검색해줘" (연도·부서·문서종류 등) - 정리·탐색: 폴더/카테고리로 묶어 UI에서 훑어보기 - 즉 내용 검색(벡터) + 조건 검색(메타데이터) 을 함께 쓰면 정확도가 올라갑니다.

KB의 메타데이터

파일 옆에 .metadata.json 사이드카 파일을 두는 방식:

{
  "metadataAttributes": {
    "service": "bedrock",
    "topic": "quota",
    "year": 2023
  }
}

→ 검색할 때 "2023년 문서만", "bedrock 주제만" 걸러서 찾습니다(메타데이터 필터). 이 꼬리표를 AI가 문서 내용을 보고 자동 생성하게 할 수도 있습니다.

IDP의 메타데이터

파일 옆 사이드카가 아니라 DB(DynamoDB)에 문서별 레코드로 저장하고, 앱이 직접 관리합니다: - file_name, file_type, status(처리 진행상태) - folder_path — 업로드한 폴더 경로 → 폴더 트리 UI - category_path — AI가 자동 분류한 카테고리(예: 인프라/Terraform) → 자동분류 UI

→ KB가 "검색 필터용 꼬리표"라면, IDP는 거기에 더해 처리 상태 추적·폴더 탐색·자동 분류까지 메타데이터로 굴립니다.

요약: 메타데이터 = 문서를 거르고 정리하는 꼬리표. 벡터 검색을 "조건 필터"로 보완합니다. 둘 다 있으나, 저장 위치(사이드카 파일 vs DB)와 활용 범위(검색 필터 vs 검색+상태+폴더+분류)가 다릅니다.

적합한 경우 표준 문서 Q&A를 빠르게 스캔본·도표·그래프·자동정리가 핵심일 때

8. 그래서 뭘 써야 하나?

  • 대부분의 "문서 올려서 챗봇으로 물어보기" → Bedrock KB가 정답에 가깝습니다. 빠르고 싸고, 파서만 강하게(BDA/Claude) 켜면 표·스캔본도 커버.
  • 스캔 문서·도면·차트·인포그래픽이 핵심이거나, 지식그래프·자동 폴더분류·페이지별 심층분석 같은 게 제품의 핵심 가치라면 → IDP 같은 커스텀이 값을 합니다. 대신 비싸고 복잡합니다.

한 줄 결론: 결과(AI 챗봇)는 비슷하다. KB는 "빠르고 싸게, 제어는 AWS에", IDP는 "무겁지만 무엇이든 직접 제어". 특별히 이미지·그래프·자동정리가 필요 없으면 KB로 충분합니다.

9. IDP는 내부에서 어떻게 동작하나 — 자세히 보기

KB는 "블랙박스 완제품"이라 내부를 몰라도 됩니다. 반면 IDP는 직접 조립한 공장이라, 파일 하나가 들어와서 검색 가능해지기까지 여러 단계를 스스로 거칩니다. 이 절은 그 과정을 순서대로 풀어씁니다.

9-1. 큰 그림 — 파일 하나가 지나는 길

9-2. 단계별로 자세히

① 업로드 & 감지 - 사용자가 웹 UI에서 파일을 올리면 S3(파일 보관함)에 저장됩니다. 웹 크롤러로 외부 페이지를 수집해 넣을 수도 있습니다. - S3에 파일이 생기면 EventBridge(AWS의 "이벤트 감시자")가 자동으로 "새 파일 도착"을 감지해 파이프라인을 시작합니다. → 사람이 "동기화" 버튼을 누를 필요가 없음.

② 타입 감지 (파싱 경로 결정) - 파일 종류(MIME 타입)를 보고 어떻게 처리할지 경로를 나눕니다. PDF·이미지는 "그림으로 보는" 경로, 워드·엑셀·CAD는 "먼저 변환하는" 경로 등. - 이게 중요한 이유: 스캔한 PDF와 엑셀 표는 완전히 다르게 다뤄야 제대로 읽히기 때문입니다.

③ 전처리 — "읽을 수 있게 만들기" (여러 방식 병렬) IDP의 핵심 특징: 한 문서를 여러 방법으로 동시에 훑어서 최대한 많은 정보를 뽑습니다. - 페이지 → 이미지 렌더링: 각 페이지를 사진처럼 이미지로 만듦 (뒤에서 AI가 "눈으로 보기" 위해). - OCR(글자 인식): 스캔본·이미지 속 글자를 텍스트로 인식. (IDP는 자체 호스팅 OCR 모델을 씀 — 이미지 기반 문서에 강함) - BDA(표·레이아웃 추출): 표·양식·레이아웃 구조를 뽑아냄. - 포맷 파서: 워드(DOCX)·PPT·엑셀(XLSX)·CAD 도면(DWG/DXF)·HTML/MD 등을 각각에 맞게 텍스트+이미지로 변환. → PDF/이미지 말고도 폭넓은 파일 종류를 지원.

즉 "파싱"이 한 가지가 아니라, 문서 성격에 맞춰 여러 엔진(이미지/OCR/BDA/포맷파서)을 병렬로 돌리는 단계입니다.

④ 세그먼트 조립 (페이지 = 한 조각) - 위에서 나온 결과(이미지 + OCR 텍스트 + 표 + 파서 텍스트)를 페이지 단위로 하나로 묶습니다. 이 묶음이 IDP의 "청크(세그먼트)"입니다. - 그래서 IDP는 5절에서 말한 대로 페이지째 자릅니다(의미/계층 청킹이 아님).

⑤ 비전 AI 분석 — "보고 이해해서 다시 쓰기" (이게 KB와 가장 다른 부분) - 각 페이지 이미지를 비전 AI(Claude)에게 직접 보여줍니다. AI는 도표·차트·표·레이아웃까지 눈으로 보고 내용을 파악합니다. - 단순히 원문 텍스트를 다시 뱉는 게 아니라, 원문 + 개요 + 핵심 정보 + 분석 노트를 새로 작성합니다. (원문 텍스트만으로는 놓치는 "그림이 말하는 내용"을 잡음) - 방식: AI가 우선 직접 이미지를 읽고, 잘 안 보이는 부분만 되물어보는 도구(analyze_image)를 선택적으로 호출하는 에이전트형(ReAct) 구조. (고정된 "질문-답변 N회 반복"이 아니라, 필요할 때만 추가로 확인) - 페이지가 많으면 여러 페이지를 병렬로 분석하되, AI 호출량이 몰리지 않게 속도 조절(throttle)을 겁니다.

⑥ 색인 (검색 가능하게 저장) - 분석 결과를 임베딩(Titan Embed V2, 1024차원)으로 숫자 벡터화한 뒤 LanceDB에 저장. - LanceDB는 하이브리드 검색 제공: 벡터(의미) + 키워드(FTS)로 찾고, 리랭커(Cohere)로 순위를 다시 매겨 정확도를 높임.

⑦ 지식그래프 (엔티티 연결) - 문서에서 인물·조직·개념(엔티티)을 뽑아 Neptune 그래프 DB에 점(노드)과 선(관계)으로 저장. → "이 개념과 연결된 문서/개념" 탐색 가능.

⑧ 요약 & 자동 분류 - 문서 전체 요약을 만들고, 카테고리(category_path)를 AI가 자동 부여해 폴더 트리에 정리.

⑨ 실시간 진행 표시 - 위 모든 단계의 진행 상황(전처리 중 / 분석 중 / 완료 등)을 WebSocket으로 화면에 실시간 중계합니다. 사용자는 "지금 몇 페이지 분석 중"인지 바로 봅니다.

9-3. 아키텍처 — 어떤 조각들로 이루어져 있나

IDP는 위 흐름을 굴리기 위해 약 14개의 인프라 스택(기능 묶음)으로 구성됩니다. 큰 덩어리로 묶으면:

계층 역할 구성 요소(예)
인제스천/저장 파일 받기·보관·감지 S3, EventBridge, 웹 크롤러
전처리 읽을 수 있게 변환 이미지 렌더링, 자체 OCR(SageMaker), BDA, 포맷 파서
오케스트레이션 단계 순서 제어·병렬화 Step Functions(분산 Map·throttle), SQS 큐
분석/AI 이해·요약·분류·엔티티 비전 분석 에이전트, 요약기, 분류기 (Claude Sonnet 4.6 + Haiku 4.5 2단 구성)
저장/검색 색인·검색·그래프 LanceDB(벡터+키워드+리랭크), Neptune(그래프), DynamoDB(메타데이터)
에이전트/대화 챗봇·검색 도구 idp-agent·research-agent, MCP 서버(검색/QA/이미지)
애플리케이션 사용자 접점 React 프론트, FastAPI 백엔드, Cognito 인증, WebSocket 실시간

핵심 요약: IDP는 "문서 → 벡터"만 하는 파이프라인이 아니라, ① 여러 방식으로 파싱 → ② 페이지를 AI가 눈으로 보고 분석 → ③ 검색·그래프·요약·분류 → ④ 인증·UI·챗봇까지 갖춘 완결된 문서 처리 플랫폼입니다. KB가 "문서→검색"을 버튼 몇 번으로 준다면, IDP는 그 각 단계를 직접 만들고 제어하는 대신 그만큼 무겁고 복잡합니다.

⚠️ 참고: 위 구성은 이 프로젝트(megazone-idp)의 실제 구조를 개념 수준으로 정리한 것입니다. 세부 스택 이름·모델 버전은 바뀔 수 있으니, 정확한 최신값은 코드(packages/infra, models.json)를 기준으로 확인하세요.

10. Bedrock KB는 내부에서 어떻게 동작하나 — 자세히 보기

KB는 "관리형"이라 핵심 엔진(파싱·청킹·임베딩·검색)은 AWS가 블랙박스로 굴립니다. 개발자는 옵션만 고르고, 그 주변에 인증·가드레일·인용·세션 같은 앱 기능을 붙입니다. 이 절은 그 안에서 실제로 무슨 일이 일어나는지 풀어씁니다.

KB의 동작은 크게 두 흐름입니다. - A. 인제스천(색인) — 문서를 넣을 때 한 번 일어나는 준비 과정. - B. 질의(응답) — 사용자가 질문할 때마다 일어나는 검색·답변 과정.

10-1. 큰 그림 — 두 개의 흐름

flowchart TD
    subgraph A["A. 인제스천 (문서를 넣을 때 · 1회)"]
        direction TB
        S3["① S3에 문서 업로드 (documents/)"]
        S3 --> ING["② Lambda가 자동으로 StartIngestionJob 실행<br/>(수동 '동기화' 불필요)"]
        ING --> PARSE["③ 파싱 (전략 택1)<br/>DEFAULT · FOUNDATION_MODEL(Claude) · DATA_AUTOMATION(BDA)"]
        PARSE --> CHUNK["④ 청킹 (전략 택1, 생성 후 변경 불가)<br/>의미 · 고정 · 계층 · 없음"]
        CHUNK --> EMB["⑤ 임베딩<br/>Titan Embed V2 (1024차원)"]
        EMB --> OSS["⑥ OpenSearch Serverless에 벡터 색인<br/>(+ .metadata.json 꼬리표 함께 저장)"]
    end

    subgraph B["B. 질의 (질문할 때마다)"]
        direction TB
        Q["① 사용자 질문"]
        Q --> GRD1["② 가드레일 검사 (입력)"]
        GRD1 --> RAG["③ RetrieveAndGenerate 호출"]
        RAG --> RET["④ 검색: 질문을 벡터로 → OpenSearch에서<br/>관련 청크 찾기 (하이브리드 + 메타데이터 필터)"]
        RET --> GEN["⑤ 생성: 찾은 청크를 Claude에 넣어 답변 작성"]
        GEN --> POST["⑥ 후처리: 인용 [n] 표시 · 관련도 스코어 · 세션 저장"]
        POST --> GRD2["⑦ 가드레일 검사 (출력) → 사용자에게 답변"]
    end

10-2. 단계별로 자세히

A. 인제스천 — 문서를 검색 가능하게 만들기

① 업로드 & ② 자동 인제스천 - 문서를 S3의 documents/ 경로에 올리면, Lambda가 자동으로 인제스천 작업(StartIngestionJob)을 시작합니다. → 콘솔에서 사람이 "동기화" 버튼을 누르지 않아도 됨(자동화된 구성).

③ 파싱 — 글자·표를 뽑아내기 (전략 3택1) KB는 파싱 방식을 하나 골라 씁니다(이 프로젝트 기본값은 FOUNDATION_MODEL, 즉 처음부터 비전 파싱이 켜져 있음): | 전략 | 방식 | 강점 | |---|---|---| | DEFAULT | 기본 텍스트 추출 | 빠르고 쌈, 디지털 텍스트 PDF에 충분 | | FOUNDATION_MODEL | Claude가 페이지를 보고 표·이미지까지 해석 | 스캔본·표·복잡한 레이아웃 | | DATA_AUTOMATION | AWS BDA로 OCR·표·레이아웃 추출 | 양식·표 많은 문서 |

FOUNDATION_MODEL/DATA_AUTOMATION로 파싱한 이미지·표 결과는 별도의 멀티모달 보관 버킷에 저장해 뒀다가 검색·인용에 활용합니다.

④ 청킹 — 조각으로 자르기 (전략 택1, 나중에 못 바꿈) 5절에서 설명한 의미/고정/계층/없음 중 하나를 고릅니다(기본 의미). ⚠️ 처음 정하면 변경하려면 데이터소스를 다시 만들어야 합니다.

⑤ 임베딩 → ⑥ 저장 - 각 조각을 Titan Embed Text V2(1024차원) 벡터로 변환. - OpenSearch Serverless에 벡터를 색인하고, 문서 옆 .metadata.json 꼬리표(연도·주제 등)도 함께 저장해 나중에 필터로 씀. - → 여기까지가 "한 번만" 일어나는 준비. 이제 검색 가능.

B. 질의 — 질문에 답하기 (질문마다 반복)

① 질문 → ② 입력 가드레일 - 사용자가 질문하면, 먼저 가드레일이 부적절한 입력(금칙어·민감정보 등)을 걸러냅니다. (IDP엔 없는, KB 구성의 강점)

③ RetrieveAndGenerate — "찾아서 답하기"를 한 번에 - AWS의 RetrieveAndGenerate API가 검색과 답변 생성을 묶어 처리합니다.

④ 검색(Retrieve) - 질문을 벡터로 바꿔 OpenSearch에서 가까운 청크를 찾습니다. - 하이브리드 검색(의미+키워드) 옵션과 메타데이터 필터("2023년 문서만" 등)를 적용해 정확도를 높입니다.

⑤ 생성(Generate) - 찾은 청크들을 Claude에 근거 자료로 넣어 답변을 생성합니다. 교체 가능한 프롬프트 템플릿으로 답변 스타일을 서버에서 조정할 수 있습니다.

⑥ 후처리 - 답변에 출처 인용 [n] 을 달고(문서·페이지 기준 중복 제거), 필요하면 2차 검색으로 관련도 점수를 매깁니다. - 대화 맥락(session id)을 DynamoDB에 저장해 다음 질문에서 이어지게 합니다(멀티턴 대화).

⑦ 출력 가드레일 → 답변 - 생성된 답변도 가드레일로 한 번 더 검사한 뒤 사용자에게 전달합니다.

참고: 이 프로젝트는 위 표준 RAG 경로 외에, Bedrock Agent(액션 그룹으로 도구 호출) 경로도 별도로 갖추고 있어, 단순 Q&A를 넘어 "작업 수행형" 시나리오도 지원합니다.

10-3. 아키텍처 — 어떤 조각들로 이루어져 있나

KB의 핵심 엔진은 AWS 관리형이라 직접 만드는 부분은 그 "주변"입니다.

계층 역할 AWS가 관리 / 직접 구축
인제스천 업로드 감지·색인 트리거 S3 + Lambda(자동 인제스천) — 직접

⚠️ 참고: 위 구성은 이 프로젝트(csc-genai-lab)의 실제 구조를 개념 수준으로 정리한 것입니다. 기본 파서·모델·청킹 등 세부값은 코드(packages/cdk_infra, cdk.json)를 기준으로 확인하세요.

11. 지식그래프는 언제 진짜 값을 하나 — 벡터검색 vs 그래프

IDP엔 Neptune 지식그래프가 있고 KB엔 없습니다. 그럼 "그래프가 있으면 뭐가 좋냐"를 오해 없이 정리합니다.

개념 차이 - 일반 검색(벡터/키워드) = "질문과 의미가 비슷한 문단"을 찾음. - 그래프 탐색 = "엔티티(사람·회사·프로젝트·제품 같은 개체)와 그들 사이의 관계"를 따라감. 문서를 분석할 때 개체를 노드, 관계를 엣지로 저장:

[김대표] --(재직)--> [메가존]
[메가존] --(계약)--> [프로젝트 A]
[프로젝트 A] --(사용)--> [Bedrock]

→ 이 노드/엣지는 어느 문서에서 나왔든 하나로 합쳐집니다.

흔한 오해 — "그래프 = 문서 간 검색"이 아니다

벡터검색도 이미 여러 문서에 걸쳐 찾습니다. 오히려 그게 벡터검색의 기본 동작입니다 — 질문을 던지면 모든 문서의 청크를 한 풀에 넣고 의미적으로 가까운 top-k를 뽑으니, 문서 5개에서 관련 문단을 섞어 가져오는 게 정상입니다. 그래서 "프로젝트 A 책임자?"처럼 어느 한 문서에 답 문장이 통째로 있으면 벡터검색이 그냥 집어옵니다.

그래프의 강점은 "여러 문서"가 아니라 "연결을 스스로 이어야 하는 질문"입니다.

그래프가 진짜 이기는 딱 3가지

① 멀티홉 — 중간 고리가 질문과 안 닮았을 때

"메가존이 수주한 프로젝트의 책임자와 같은 부서 사람들 명단"

메가존→프로젝트A(문서1) → 프로젝트A→김대표(문서2) → 김대표→영업부(문서3) → 영업부→명단(문서4)를 차례로 이어야 답이 나옵니다. 벡터검색은 "영업부 명단" 청크가 원 질문과 의미적으로 안 닮아 top-k에서 놓칠 수 있습니다. 그래프는 엣지를 따라 확실히 도달.

② 전수 집계·열거 — "모든 X"

"우리가 계약한 모든 회사 목록"

벡터검색은 top-k(예: 10개)만 반환 → 15개면 5개 누락. 그래프는 계약 엣지를 전부 순회할 수 있습니다.

③ 구조적 관계 질문

"누가 누구에게 보고하나 / 조직도 / 이 부품이 들어가는 모든 제품"

관계 자체가 답인 질문. 벡터검색은 텍스트 유사도라 구조를 셈하지 못합니다.

질문 유형 벡터검색(KB) 그래프
"X에 대해 알려줘" / 여러 문서에서 관련 내용 찾기 ✅ 잘 됨 ❌ 불필요
멀티홉 연결 추론 ⚠️ 놓칠 수 있음 ✅
"모든 X 열거" 전수 집계 ❌ top-k 한계 ✅
조직도·보고체계·부품 구성 ❌ ✅

이 프로젝트(IDP)에서 실제로

  • 엔티티 추출(entity-extractor) — 세그먼트마다 LLM이 개체를 뽑음
  • 엔티티 정규화 — "김 대표", "김OO 대표", "대표님"을 같은 노드로 통합. ← 이게 핵심 난이도. 안 하면 그래프가 파편화됨
  • 그래프 구축(graph-builder → graph-service) — Neptune에 upsert
  • 채팅 시 그래프 탐색(traversal) — 연결된 페이지를 찾아옴

정직한 판단 기준

그래프는 강력하지만 가장 무거운 부분입니다 — Neptune(서버리스) 비용 + 엔티티 정규화 품질이 그래프 유용성을 통째로 좌우합니다. 정규화가 부실하면 노드가 파편화돼 오히려 노이즈가 됩니다.

판단 기준: "우리 제품의 대표 질문이 여러 문서를 이어야만/전수로 답이 나오는 종류인가?" - 예(관계·이력·조직·부품 추적이 핵심) → 그래프 유지. - 아니오(대부분 "이 문서/이 주제 안에서 찾기") → Neptune을 통째로 걷어내고 벡터 검색만으로 충분. Bedrock KB를 쓰면 이 부분이 아예 없어짐.

솔직한 현실: 회사 자료 챗봇의 질문 대부분은 첫 줄(단순 검색)입니다. 그래프는 위 ②·③(전수 집계, 조직/관계 추적)이 제품의 대표 질문일 때만 값을 합니다.

12. 가장 큰 철학 차이 — "무엇을 색인하는가"

둘 다 "PDF → 검색 가능"이라는 결과는 같지만, 실제로 저장(색인)하는 대상이 다릅니다. 이게 KB와 IDP를 가르는 가장 본질적인 차이입니다.

  • KB = "자르고 담는다" (chunk → embed → store): 원문 텍스트를 청크로 잘라 그대로 임베딩. 빠르고 싸고, 텍스트 PDF엔 충분.
  • IDP = "이해하고 담는다" (page → 비전 분석 → embed the analysis): 페이지를 이미지로 보고, 비전 AI가 이해해서 새로 쓴 분석문+Q&A를 임베딩. 색인 대상이 원문이 아니라 "AI의 이해".

IDP의 PDF 처리 — 한 페이지가 4갈래로 동시에 뜯긴다

  1. 전처리(병렬): 텍스트 추출 + OCR(PaddleOCR) + BDA(표·레이아웃) + 페이지를 이미지로 렌더링. → PDF를 텍스트로만 안 보고 "그림"으로도 확보.
  2. SegmentBuilder: 페이지마다 위 결과를 하나로 병합한 세그먼트 JSON 생성. json { "segment_type": "PAGE", "image_uri": "page_0000.png", "paddleocr": "...", "format_parser": "...", "bda_indexer": "..." }
  3. ⭐ SegmentAnalyzer — 페이지를 "보는" ReAct 비전 에이전트 (여러 페이지 병렬): 각 페이지에 대해 Claude Sonnet 4.6이 페이지 이미지 + OCR/BDA/텍스트를 함께 받아, 스스로 질문을 만들고 → 필요한 도구를 호출하고 → 답을 종합하는 걸 필요한 만큼 반복. 차트·도표·그림·레이아웃을 시각적으로 이해해 구조화된 분석·Q&A를 생성. → 나오는 건 "원문 텍스트"가 아니라 "LLM이 그 페이지를 이해해서 쓴 분석문 + Q&A".
  4. 색인 대상 = 원문이 아니라 "분석 결과": 분석문을 Titan Embed V2(1024차원)로 임베딩 → LanceDB(벡터 + 전문검색 FTS). 동시에 엔티티 추출 → Neptune, 문서 요약(Haiku) → 자동 분류.
  5. 완료: 채팅 시 하이브리드 검색(벡터+키워드) + Cohere 리랭크.

KB의 PDF 처리 — 훨씬 짧고 텍스트 중심

  1. Parsing: PDF에서 텍스트 추출 (기본 파서 / FM 고급 파싱 / BDA 중 선택).
  2. Chunking: 텍스트를 청크로 분할 (의미/고정/계층/없음).
  3. Embedding: 청크를 Titan Embed V2로 벡터화.
  4. Store: 벡터DB(OpenSearch Serverless 등)에 저장.
  5. Retrieve: RetrieveAndGenerate로 의미검색(+리랭크+메타데이터 필터).

→ 색인 대상 = 원문 텍스트 청크 그대로.

부록 — 용어 빠른 사전

  • RAG: 문서를 미리 색인해두고, 질문에 맞는 조각을 꺼내 AI가 답하게 하는 방식.
  • 임베딩(Embedding): 글을 "의미가 담긴 숫자 벡터"로 바꾸는 것. 비슷한 뜻이면 벡터도 가깝다 → 의미 검색 가능.
  • 벡터 검색: 질문을 벡터로 바꿔, 가까운 문서 조각을 찾는 것.
  • 청크(Chunk): 문서를 자른 조각.
  • 파싱(Parsing): 파일에서 글자·표를 뽑아내는 것.
  • OCR: 이미지/스캔에서 글자를 인식.
  • 토큰(Token): AI가 세는 글자 단위(≈ 단어 조각).
  • 지식그래프: 문서 속 인물·조직·개념을 점(노드)과 선(관계)으로 연결한 지도.
  • 메타데이터: 내용이 아닌, 문서에 붙은 꼬리표(종류·주제·폴더 등).
  • BDA: 표·양식·레이아웃 구조를 뽑아내는 AWS 문서 자동화 기능.
  • 리랭크(Rerank): 1차로 찾은 검색 결과의 순위를 전용 모델로 다시 매겨 정확도를 높이는 것.
  • 하이브리드 검색: 의미(벡터) 검색과 키워드 검색을 함께 써서 찾는 방식.
  • 에이전트(ReAct): AI가 스스로 판단해 필요할 때 도구를 호출하며 문제를 푸는 방식.
  • WebSocket: 서버가 화면으로 진행 상황을 실시간으로 밀어 보내는 통신 방식.
  • EventBridge: "새 파일이 생겼다" 같은 사건을 감지해 자동으로 다음 작업을 트리거하는 AWS 서비스.
  • 멀티홉(Multi-hop): 답 하나를 얻기 위해 여러 개의 연결(A→B→C…)을 차례로 이어야 하는 질문.
  • 엔티티 정규화: 같은 대상을 가리키는 서로 다른 표현("김 대표"·"대표님")을 하나의 노드로 합치는 것.
  • top-k: 검색에서 가장 관련 높은 상위 k개만 뽑는 것. "모든 X"를 물으면 k를 넘는 항목은 누락될 수 있음.
  • FTS(전문검색): 단어가 실제로 포함됐는지로 찾는 키워드 검색. 벡터(의미) 검색과 함께 쓰면 하이브리드.
