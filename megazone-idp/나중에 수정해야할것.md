## 1.5. 기본 워크스페이스 language null → 채팅 크래시 (실deploy에서 발견)
- [ ] **증상**: 문서 업로드·색인은 되는데 **채팅 답변이 안 나옴**. idp-agent 런타임 로그: `ProjectItem.model_validate(item)` → `pydantic ValidationError: string_type` (language).

- [ ] **임시조치(적용됨)**: 해당 프로젝트 DDB 레코드 `data.language`를 `"ko"`로 수동 세팅. → **신규 워크스페이스는 여전히 재발**.
- [x] **영구 수정 2곳** (완료):
  1. **백엔드** `routers/projects.py` — `DEFAULT_PROJECT_LANGUAGE="ko"` 추가. `get_default_project`(기본워크스페이스)·`create_project`(`request.language or DEFAULT`) 둘 다 null 금지. 프론트 fallback `POST {name}` 경로 커버됨.
  2. **에이전트** `packages/agents/idp-agent/helpers.py` — `ProjectData.language`를 `str | None = "en"`로 변경(null이어도 검증 통과, 크래시 X).
- 교훈: 백엔드-에이전트가 **같은 DDB 아이템을 서로 다른 pydantic 모델로 검증** → 한쪽이 느슨(Optional)하고 한쪽이 엄격(required)하면 런타임 크래시. 공유 스키마/계약 정렬 필요.

## 1.7. 지원 파일타입 / 분류 품질 (실사용에서 발견)
- [x] **HTML 미지원 → 분석 안 됨** (완료). `.html`/`.htm`이 `type-detection` MIME 맵에 없어 `application/octet-stream`으로 처리 → 텍스트 추출 경로를 못 탐. 조치: type-detection MIME 맵 + `is_text`에 `text/html` 추가, `format-parser` `TEXT_MIME_TYPES` + `_strip_html`(태그/script/style 제거) 추가.
- [ ] **기타 미지원 포맷 검토** — 지원 목록: pdf·docx·doc·txt·md·html·csv·xlsx·xls·이미지·pptx·ppt·webreq·dxf. 필요 시 추가 검토: `.json`, `.rtf`, `.odt`, `.eml`, `.pptx` 외 등. 미지원 확장자는 octet-stream으로 조용히 실패하니 **업로드 시 지원포맷 화이트리스트/안내** 추가 권장.
- [ ] **카테고리 분류 품질 후속** (프롬프트 1차 개선은 적용됨: 파일명·업로드폴더·도메인 가이드). 추가 개선 여지:
  - 요약뿐 아니라 **원문 일부/확장자 규칙**을 신호로 사용 (예: `.tf`/`tfplan`→인프라, `.sql`→데이터 등 결정적 힌트).
  - **저신뢰(confidence 낮음) 재검토**: 임계값 이하는 "미분류"로 보류 후 배치 재분류.
  - **기존 문서 일괄 재분류** 기능 (프롬프트 개선 후 소급 적용 — 현재는 재업로드해야 재분류됨).
  - 프로젝트 택소노미가 커질 때 **요약 임베딩 재클러스터링**으로 폴더 구조 재정리 (SPEC R3 후속).

## 1.8. 문서 삭제 시 검색 인덱스(LanceDB) 정리 누락 — 삭제해도 챗봇이 옛 문서 참조 (실사용에서 발견)
- [ ] **증상**: 문서를 (일괄)삭제했는데도 챗봇이 삭제된 문서(예: "AWS 아키텍처", "NanoH2O 규격서")를 계속 검색해서 답함. DDB에는 문서 없음(META만), Neptune 그래프도 비어있음(clear_all=0). **진짜 원인은 LanceDB 인덱스에 레코드 잔존**(확인: `count`=5).
- [ ] **원인 2가지**:
  1. `backend/app/routers/documents.py` `delete_document`이 `lancedb_delete_by_workflow`를 **best-effort**로 호출 — 실패해도 `lancedb_error`만 기록하고 삭제는 "성공" 처리 → 인덱스에 레코드 잔류. 삭제 성공/실패를 사용자에게 반영하거나 재시도 필요.
  2. `delete_by_workflow`는 **프로젝트 QA 테이블만** 지우고 **`GRAPH_KEYWORDS_TABLE`(교차문서 키워드 인덱스)은 안 지움** → 태그클라우드/키워드검색에 잔재. 삭제 흐름에 `delete_graph_keywords_by_project_id`(또는 workflow별) 호출 추가 필요.
- [ ] **임시조치(적용됨)**: lance-service 직접 invoke — `drop_table`(프로젝트 테이블 5개 제거) + `delete_graph_keywords_by_project_id` → `count`=0 확인.
- [x] **영구 수정** (완료, `routers/documents.py` `delete_document`):
  - ① LanceDB 정리 보장 — `lancedb_delete_by_workflow`를 **3회 재시도**, 끝내 실패하면 S3/DDB 삭제 전에 **HTTP 502로 중단**(고아 인덱스 방지, 사용자에 실패 노출).
  - ②③ **마지막 문서 삭제 시** 프로젝트 인덱스 테이블 `drop_table` + `delete_graph_keywords_by_project_id` 호출(`project_emptied` 플래그).
  - ⚠️ **주의**: `graph_keywords` 테이블 스키마에 `workflow_id`/`document_id` 컬럼이 **없고 project_id만** 있음(`lancedb-service/src/db/model.rs` `keyword_record_schema`). 따라서 **문서 단위 키워드 삭제는 스키마상 불가** → 프로젝트가 비었을 때만 전체 삭제 가능. 문서별 키워드 정리가 필요하면 스키마에 doc/wf 키 추가 + 재색인 필요(별도 작업).
- [ ] **관련**: Neptune orphan_cleanup도 **병렬 일괄삭제 시 레이스**로 고아 엔티티가 남을 수 있음(각 워크플로 삭제 메시지마다 프로젝트 전역 orphan_cleanup 실행 → 다른 문서가 아직 있으면 0 삭제). 모든 삭제 완료 후 orphan_cleanup을 1회 보장하거나, 마지막 문서 삭제 시 `clear_all`/전역 정리 트리거 고려.
- 참고: 삭제해도 챗봇이 옛 문서를 언급하면 **채팅 세션 기억(S3)** 때문일 수도 있음(검색 인덱스가 아니라 대화 히스토리). 새 채팅으로 확인. 세션 정리 정책도 검토 대상.
