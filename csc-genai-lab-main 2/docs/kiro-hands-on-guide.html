00사전 준비

USER 실습 시작 전 갖춰야 하는 것
  • Kiro IDE 설치 및 로그인 — 최신 버전 권장. 이 리포는 .kiro/skills에 배포 지침을 이미 포함하고 있어, Kiro에서 이 리포를 workspace로 열기만 하면 스킬이 자동으로 매칭됨.
  • AWS 계정과 관리자(admin) 권한 프로파일 — 배포 스킬은 EC2/CDK/Bedrock/IAM/S3 등 전 영역을 다루므로 AdministratorAccess 상당의 프로파일이 필요.

이 실습은 편의상 AdministratorAccess 프로파일로 진행합니다. 운영 환경에서 최소 권한(least privilege)으로 좁히고 싶다면 부록 B. 최소 권한 참고를 확인하세요.

USER 배포 전 사전작업 — 미리 해두면 배포가 안 막힘

0-1. Bedrock에서 Claude 모델 활성화 확인

AWS 콘솔 → Bedrock → Model access에서 Claude 모델이 활성화돼 있는지 먼저 확인하세요. 활성화 요청 시 회사 사이트, 사용 목적 등을 입력하고 등록하면 승인 안내 메일이 옵니다. 승인 후 Bedrock Playground → Chat에서 Claude Sonnet 4.5로 응답이 정상적으로 오는지 한 번 테스트해 두면 배포 뒤 챗봇 검증이 수월합니다.

0-2. Lambda 동시성(Concurrency) 한도 증가 요청

Lambda 계정 동시성 한도를 100~1000 사이로 올려 두세요. Service Quotas에서 Concurrent executions 증가를 요청합니다.

1000으로 요청하면 즉시 반영되지 않습니다. 승인까지 시간이 걸리므로 배포 일정보다 미리 신청해 두는 것이 좋습니다.

0-3. (Windows) Kiro 실행 권한 열기

Windows에서 Kiro를 처음 설치했다면 PowerShell 실행 정책 때문에 스크립트가 막힐 수 있습니다. PowerShell에서 아래 명령을 실행한 뒤, Kiro 창을 닫고 관리자 권한으로 다시 실행하세요.

# 현재 실행 정책 확인
Get-ExecutionPolicy

# 현재 사용자에 한해 RemoteSigned로 변경
Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

01Set up(로컬)

USER 로컬 환경 준비 — 딱 세 가지

1-1. AWS CLI 설치 + 프로파일 구성

AWS CLI v2 설치 — OS에 맞는 방법을 하나 고르세요. 자세한 공식 가이드는 AWS CLI 설치 문서 참고.

macOS

# 방법 A. Homebrew
brew install awscli

# 방법 B. 공식 pkg 인스톨러
curl "https://awscli.amazonaws.com/AWSCLIV2.pkg" -o "/tmp/AWSCLIV2.pkg"
sudo installer -pkg /tmp/AWSCLIV2.pkg -target /

Windows (PowerShell, 관리자 권한)

# 방법 A. MSI 인스톨러 (권장)
msiexec.exe /i https://awscli.amazonaws.com/AWSCLIV2.msi

# 방법 B. winget
winget install -e --id Amazon.AWSCLI

# 방법 C. Chocolatey
choco install awscli

설치 후 새 PowerShell/터미널 창을 열어야 aws 명령이 PATH에 잡힘.

Linux (x86_64)

# Ubuntu/Debian/RHEL/Amazon Linux 공통 — 공식 zip 인스톨러
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "/tmp/awscliv2.zip"
unzip -q /tmp/awscliv2.zip -d /tmp
sudo /tmp/aws/install

ARM64(Graviton, Apple Silicon Linux VM 등)라면 URL을 awscli-exe-linux-aarch64.zip으로 바꿔 실행. 패키지 매니저의 apt install awscli, yum install awscli는 v1이 설치될 수 있어 권장하지 않음 — 이 실습은 v2 기준.

설치 확인 + 프로파일 구성 (모든 OS 공통)

aws --version                              # aws-cli/2.x.x 이 나와야 v2
aws configure --profile <프로파일명>        # Access Key / Secret Key / Default region / Output format 입력
aws sts get-caller-identity --profile <프로파일명>   # Account/Arn이 뜨면 성공

Windows는 cmd.exe/PowerShell 어느 쪽이든 동일 명령이 동작. 이후 실습 문서의 예시는 대부분 bash/zsh 문법(백슬래시 라인 연속, 작은따옴표 JSON) 기준이라, Windows에서는 Git Bash나 WSL을 쓰면 예제를 그대로 붙여넣을 수 있어 편합니다.

1-2. 프로젝트 내려받기 (S3)

프로젝트 zip은 아래 명령으로 내려받을 수 있습니다. zip에 genai_lab_kiro 폴더가 들어 있어, 명령을 실행한 위치에 genai_lab_kiro 폴더로 풀립니다.

Kiro IDE → File → Open Folder → 방금 압축 해제한 genai_lab_kiro 폴더. 사이드바에 .kiro/skills/ec2-ssm-cdk-deploy가 보이면 배포 스킬이 매칭될 준비가 된 것.

로컬에 Node/pnpm/Docker/CDK를 설치할 필요가 없습니다. 이 실습은 배포 자체를 EC2에서 수행합니다(Kiro가 EC2를 만들고, 도구 설치까지 원격에서 진행). 로컬은 AWS CLI만 있으면 충분.

KIRO 2-3. 배포 전 자동 사전 점검

값을 넘기면 Kiro가 배포에 들어가기 전에 다음을 자동 검사합니다 (사용자 개입 불필요):

  1. CDK bootstrap 상태: 스택뿐 아니라 assets 버킷·SSM 버전 파라미터까지 함께 조회해서 drift(스택만 남고 버킷 삭제) 여부 판정.
  2. 리전별 하드코딩 코드: Bedrock 인퍼런스 프로파일(us. / eu. / apac. / global.) 접두사, cdk.json의 chat:defaultModelId, UI의 ModelChipDropdown, chat-summary-with-sessionid.ts의 Nova ARN 등을 입력 리전에 맞춰 수정.
  3. CDK 라이브러리 호환성: @cdklabs/generative-ai-cdk-constructs ↔ aws-cdk-lib/constructs peer 확인. 안 맞으면 배포가 synth 단계에서 실패.
  4. 고정이름 IAM 역할 리전 충돌: 다른 리전에 이미 배포된 이력이 있으면 AmazonBedrockExecutionRoleForKnowledgeBase* 같은 역할이 IAM(글로벌)에서 재사용돼 배포 리전 리소스를 못 잡는 문제가 발생할 수 있어 사전 점검.

03Deploy(Kiro가 자동으로 EC2·SSM 실행)

KIRO 프롬프트·입력값 확정 후 자동 수행

사용자는 로그를 지켜보기만 하면 됩니다.

  1. IAM Role/Instance Profile 생성 — GenAILabDeployRole (AdministratorAccess + AmazonSSMManagedInstanceCore). 이 EC2 역할을 최소 권한으로 좁히는 방법은 부록 B 참고.
  2. VPC/서브넷/보안그룹 준비 — 모드에 따라 default 조회 / existing 검증 / new 신규 생성.
  3. EC2 인스턴스 생성 — Amazon Linux 2023, t3.large, gp3 30GB, 퍼블릭 IP. SSM 등록까지 대기.
  4. 로컬 소스 → S3 → EC2 전송 — Kiro가 로컬 리포를 tar로 묶어 genailab-deploy-<계정ID> S3 버킷에 업로드하고, EC2에서 SSM으로 내려받아 압축 해제. node_modules·.git·cdk.out은 제외되므로 항상 최신 로컬 코드가 반영.
  5. remote-deploy.sh 백그라운드 실행 — setsid ... </dev/null & disown으로 SSM 세션과 분리 실행(SSM 타임아웃/이중 실행 방지). 스크립트가 EC2에서 도구 설치 → pnpm install → OpenAPI 스키마 생성 → cdk bootstrap(필요 시) → vite build → cdk deploy --all 순서로 진행.
  6. 로그 tail — Kiro가 /tmp/deploy.log를 주기적으로 조회해서 DEPLOY_DONE 마커 또는 오류 문구를 감지.
  7. deploy_list.json 갱신 — 생성된 모든 리소스(EC2·SG·IAM·VPC·S3·CDK 스택·WebsiteUrl)를 이 파일에 기록. 이후 6장 정리에서 이 파일을 참조.

소요 시간: 정상 케이스에서 20~40분. WebsiteStack의 CloudFront 배포와 KB/OpenSearch Serverless 컬렉션 생성이 가장 오래 걸림. 화면이 멈춘 것처럼 보여도 실제로는 진행 중이므로 인내가 필요합니다.

04Troubleshooting

Kiro는 로그에서 오류를 발견하면 스스로 진단·수정·재시도합니다(최대 5회). 사용자 개입이 필요한 경우와, 자주 마주치는 케이스만 정리.

USER 4-1. 사용자 개입이 필요한 경우
  • AWS 리전 자체가 Bedrock 미지원 — 다른 리전으로 옮기고 재배포. Kiro가 코드의 리전 하드코딩까지 함께 갱신.
  • IAM 권한 부족 (AccessDenied 배포 도중) — 프로파일이 admin이 아닌 경우. 권한 보강 후 재시도.
KIRO 4-2. Kiro가 자동으로 처리하는 실패 패턴

로그에 아래가 뜨더라도 대부분 Kiro가 알아서 복구합니다. destroy 후 재배포가 필요한 경우는 드뭅니다.

BOTH 4-4. 실습 — 챗봇 오류를 Kiro로 직접 고쳐보기

이 실습은 오류가 나도록 준비되어 있습니다. 배포는 성공했는데 챗봇만 답을 못 하는 상태가 하나 남아 있습니다. 지금까지는 Kiro가 배포 로그를 보고 스스로 고쳤다면, 여기서는 화면에 뜬 오류 메시지를 여러분이 Kiro에게 넘겨 고치는 흐름을 연습합니다.

1. 증상 확인 — 5장으로 넘어가 로그인한 뒤 챗봇에 아무 질문이나 던져 보세요. 답변 대신 이런 오류가 뜹니다.

AccessDeniedException: User: arn:aws:sts::<계정>:assumed-role/...IdentityPool.../CognitoIdentityCredentials
is not authorized to perform: lambda:InvokeFunction on resource:
arn:aws:lambda:<리전>:<계정>:function:...QnAAgentStreaming...
because no identity-based policy allows the lambda:InvokeFunction action

2. Kiro에게 그대로 넘기기 — 오류 메시지를 복사해서 붙여넣고 고쳐달라고 지시합니다. 원인을 여러분이 먼저 알아낼 필요는 없습니다.

"챗봇에서 질문하니까 아래 오류가 떠. 원인 찾아서 고쳐줘. 고친 뒤에는 실제로 답변이 나오는지 확인까지 해줘."

(여기에 위 오류 메시지 전문을 붙여넣기)

3. Kiro가 하는 일 — 스스로 진단하고 고칩니다. 사용자는 결과만 확인하면 됩니다.

  • 오류의 주체(Cognito 인증 역할)와 대상(스트리밍 Lambda)을 읽어내고, 브라우저가 그 함수를 직접 호출하는 구조임을 코드에서 확인.
  • 해당 역할에 호출 권한을 부여하고, 재배포 때 또 사라지지 않도록 CDK 코드에 반영할지도 함께 제안.
  • 고친 뒤 실제로 질문을 던져 답변이 나오는지 검증.

4. 확인 — 다시 질문했을 때 오류 없이 답변이 흘러나오면 성공입니다. 안 되면 오류가 바뀌었는지를 보고, 바뀐 메시지를 다시 Kiro에게 넘기세요. 오류가 바뀐다는 것은 앞 단계가 풀렸다는 뜻입니다.

이 실습에서 가져갈 것 — 배포가 전부 성공으로 끝나도 동작이 보장되지는 않습니다. 특히 CDK 밖에서 손으로 넣은 설정은 스택을 다시 세울 때 함께 사라집니다(역할·함수가 새 이름으로 만들어지므로). 같은 이유로 문서나 스크립트에 적힌 이전 환경의 버킷·인스턴스 이름을 그대로 쓰면 안 됩니다.

BOTH 4-3. destroy → 재배포가 필요한 진짜 최후 케이스

cdk destroy 후 재배포는 아래 경우만 권장. 시간 소모가 크기 때문에 웬만하면 부분 재시도로 해결합니다.

  • CDKToolkit 부트스트랩 drift가 반복 정리해도 안 잡히는 경우.
  • 여러 리전에서 배포/삭제를 반복하다 고정이름 IAM 역할이 완전히 꼬여버린 경우.
  • 사용자가 코드 구조를 크게 바꿔서 스택 이름/의존성이 어긋난 경우.

이럴 땐 Kiro에게 "리소스 정리해줘"로 6장을 먼저 돌리고, 다시 "배포해줘"로 2장부터 반복.

USER 5-2. 기본 문서로 챗봇 질답

시드된 KB 데이터소스의 기본 문서를 대상으로 챗봇에 질문. 답변 우측 근거 문서와 관련도 점수가 함께 뜨는지 확인.

  • 답변은 한 글자씩 흘러나옵니다 — 브라우저가 스트리밍 Lambda를 직접 호출하는 구조라, 검색 중에는 상태 문구가 먼저 뜨고 이어서 본문이 타이핑됩니다.
  • 그림은 본문 중간에 끼어 들어갑니다 — 답변이 인용한 페이지의 그림만, 그 단계를 설명하는 문단 뒤에 붙습니다. 관련 그림이 없으면 붙지 않는 것이 정상입니다(틀린 그림보다 없는 편이 낫다는 기준).
  • "응답이 도중에 끊겼습니다"가 뜨면 전송이 중단된 것이니 다시 질문하면 됩니다.
  • 답변 대신 AccessDeniedException ... lambda:InvokeFunction이 뜬다면 4-4 실습의 상태입니다 — 오류 메시지를 Kiro에게 넘겨 고쳐보세요.
USER 5-3. 개인 문서 업로드 후 재질답

지원 형식과 크기

  • 형식: PDF · DOCX · XLSX · CSV · TXT · MD · HTML.
  • 첫 업로드는 1~4 MB PDF 권장 — 4단계 파이프라인의 "AI 문서 분석 → 메타데이터 자동 생성"까지 실제로 채워지는 걸 눈으로 확인 가능.
  • 20 MiB 초과 파일은 자동 메타데이터·전사가 스킵되고 곧바로 벡터화로 넘어감(메타데이터는 UI에서 수동 입력 가능). 실제로 막는 것은 파일 크기가 아니라 페이지 수다 — 실측에서 6.85 MiB / 210페이지는 통과, 6.92 MiB / 350페이지는 모델이 거부.
  • 50 MB 초과 파일은 Bedrock KB S3 데이터소스가 인제스션에서 스킵 (AWS 문서).

형식마다 처리 방식이 다릅니다

  • PDF · DOCX — 페이지를 모델이 읽어 전사본(.text.md)을 함께 색인합니다. 표나 스크린샷처럼 그림 안에 갇힌 글자를 검색 가능하게 만들고, 답변에 그림을 끼워 넣는 근거가 됩니다. 페이지 수에 따라 수 분 걸립니다.
  • XLSX — 모델을 부르지 않고 시트를 마크다운 표로 변환합니다(시트 1개 = 절 1개). 표 안에서 열 이름을 주기적으로 반복하므로, 청크가 어디서 잘려도 값이 어느 열의 것인지 남습니다. 486 KB · 9시트 기준 약 24초.
  • CSV · TXT · MD · HTML — 이미 텍스트라 그대로 색인합니다(전사 없음).
  1. 좌측 메뉴 지식 베이스 → 문서 관리로 이동.
  2. 문서 업로드 → 4단계(업로드 → 분석 → 메타데이터 → 벡터화)가 끝까지 진행되는지 확인. 엑셀이라면 시트 이름이 근거 문서에 절로 잡히는지, 열 이름이 필요한 질문(예: "수행주체가 A인 항목만")에 정확히 답하는지 함께 확인.
  3. 벡터화 완료 후 지식 베이스 Q&A에서 새 문서 내용에 대해 질문 → 답변과 우측 근거 문서에 방금 올린 문서가 잡히는지 확인.
  4. 챗봇 헤더에서 모델, 프롬프트, 가드레일 칩을 바꿔가며 답변 톤/형식이 즉시 바뀌는지 확인(재배포 불필요).
USER 5-4. 가드레일 · PII 마스킹 검증

기본 가드레일(default-phone-masking)이 미리 준비되어 있습니다.

APPENDIX
부록 — 개념 정리와 최소 권한 참고

부록 A. 자주 헷갈리는 개념

  • 왜 로컬이 아니라 EC2에서 배포하나? — Lambda 번들링에 Docker가 필요하고, 사내 노트북 환경(회사 프록시, Docker 라이선스, Python 버전)마다 실패 원인이 달라짐. EC2를 배포용 빌드 박스로 두면 환경 편차를 없앨 수 있음.
  • 재배포해도 프론트 코드를 손댈 필요가 없나? — 없음. API URL과 Cognito ID 같은 값은 CDK가 배포 시점에 사이트에 자동 주입. 같은 빌드 결과물을 리전·계정 바꿔 그대로 재배포 가능.
  • deploy_list.json이란? — 배포/삭제 스킬을 이어주는 상태 파일. 배포가 중간에 끊겨도 이 파일에 기록된 리소스는 destroy 스킬이 인식해서 정리 가능. 함부로 삭제하지 마세요.
  • 고정이름 IAM 역할이 왜 문제? — AmazonBedrockExecutionRoleForKnowledgeBase* 같은 역할은 이름이 고정이라 IAM(글로벌 서비스)에서 리전 간에 이름이 겹침. 서울에서 먼저 배포한 뒤 도쿄에 배포하면, 도쿄 배포가 서울에서 만든 역할을 재사용해 서울 리소스만 가리키는 상황이 발생. 실습 중에는 한 번에 한 리전만 사용을 권장.

부록 B. 최소 권한 참고 (least privilege)

실습은 AdministratorAccess로 진행하지만, 운영에서 권한을 좁히려면 권한 주체가 둘로 나뉜다는 점을 먼저 이해해야 합니다. 이 구분이 최소 권한 설계의 핵심입니다.

B-2. EC2 인스턴스 역할 (B) — 권장: 부트스트랩 역할에 위임

cdk deploy는 실제로는 부트스트랩이 만든 역할(cdk-hnb659fds-*)을 AssumeRole해서 동작하고, 리소스 생성은 그 cfn-exec-role(기본 AdministratorAccess 보유)이 CloudFormation을 통해 수행합니다. 따라서 대상 리전이 이미 부트스트랩되어 있다면 EC2 역할은 아래 + AmazonSSMManagedInstanceCore만으로 충분합니다.

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "sts:AssumeRole",
      "Resource": "arn:aws:iam::<ACCT>:role/cdk-hnb659fds-*" },
    { "Effect": "Allow", "Action": ["ssm:GetParameter"],
      "Resource": "arn:aws:ssm:*:<ACCT>:parameter/cdk-bootstrap/*" },
    { "Effect": "Allow", "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::genailab-deploy-<ACCT>/*" }
  ]
}

팁: 미부트스트랩 리전이라면 로컬(A) 프로파일로 cdk bootstrap을 한 번 먼저 실행해 두세요. 그러면 강한 권한이 CDK가 관리하는 역할 안에 격리되고, EC2 역할은 위 최소 권한만으로 배포가 됩니다. 이것이 실무적으로 가장 깔끔한 least privilege 구성입니다.

B-3. EC2에서 직접 부트스트랩+배포하는 경우 (스킬 기본 흐름)

스킬은 EC2에서 부트스트랩과 배포를 모두 수행하므로, 이 경우 실제 생성되는 서비스 전반에 create/update/delete가 필요합니다. 스택별 실제 리소스는 다음과 같습니다.

스택생성 리소스필요 서비스
CommonStack액세스 로그 S3, Lambda Layer, Cognito User Pool/Client/Identity Pool/그룹/유저, 인증 역할·정책s3, lambda, cognito-idp, cognito-identity, iam
BedrockKnowledgeBaseStackKB 데이터/보조 S3, OpenSearch Serverless 컬렉션+인덱스, Bedrock KB+데이터소스, 인제스트 Lambda, S3 이벤트, 커스텀 리소스s3, aoss, bedrock, bedrock-agent, lambda, iam, logs
BedrockAgentsStackBedrock Agent+Alias+ActionGroup, Python Lambda(Docker 번들), CloudWatch 대시보드bedrock, bedrock-agent, lambda, cloudwatch, iam, logs, ecr
BasicRestApiStackDynamoDB 테이블, 다수 Lambda, API Gateway REST API+Cognito Authorizer, Guardrail 시드(커스텀 리소스)dynamodb, lambda, apigateway, bedrock, cognito-idp, iam, logs

이 방식은 iam:CreateRole + iam:PassRole + iam:AttachRolePolicy 조합이 필요한데, 이는 사실상 권한 상승이 가능한 조합이라 스택이 만드는 역할 범위로 좁히기 어렵습니다. 스킬이 EC2 역할에 AdministratorAccess를 쓰는 근본 이유가 이것입니다. 완전 자동(미부트스트랩 리전까지 EC2가 혼자 처리)을 유지하려면 사실상 admin 수준 권한이 불가피하므로, 권한을 줄이려면 B-2 방식을 권장합니다.
